WeatherMind AI

Personalized weather & recommendation platform. Converts raw forecast data into guidance tailored to who the user actually is — not just what the temperature says.

weatherapp — Next.js 15 recommendation-service — Node.js Open-Meteo OpenAI / Groq MongoDB

01Overview & Objective

WeatherMind AI converts raw weather data into personalized, human-readable guidance based on who the user is — age, work, hobbies, and health context — not just the raw forecast. The system is split into two independently deployable services so the AI/recommendation logic can scale and iterate separately from the weather-display frontend, and can be reused later by a mobile client.

Out of scope for this TRD: payments, team workspaces, white-label dashboards, public API — all remain Future Features, unchanged from the v1 TRD.

02Architecture Overview

weatherapp/ (Next.js frontend) recommendation-service/ (Node + Express) ┌─────────────────────────┐ ┌──────────────────────────────┐ │ Search bar │ HTTP │ Onboarding data processing │ │ Current weather │──────▶│ Rule engine (deterministic) │ │ Daily / Weekly / Monthly │◀──────│ AI layer (OpenAI / Groq) │ │ Onboarding flow │ JSON │ Recommendation API │ │ Open-Meteo calls │ │ User profile storage │ └─────────────────────────┘ └──────────────────────────────┘ │ │ ▼ ▼ Open-Meteo APIs MongoDB (profiles) (weather / geocoding / OpenAI / Groq (AI calls) air quality)
Design rationale: the frontend never talks to MongoDB or the AI provider directly. It calls its own weather logic (Open-Meteo, no key needed) and calls the recommendation service for anything involving user profile data or AI. This keeps the AI API key and all sensitive onboarding data fully server-side, behind one clear security boundary.

07SAQ — Security, Assumptions & Open Questions

7.1 Security

  • Health-related fields (healthConsiderations) shall be encrypted at rest (MongoDB field-level encryption or app-layer encryption before write).
  • All recommendation-service endpoints require a valid session token — no anonymous access to profile or AI endpoints.
  • AI provider API key lives only in recommendation-service environment variables — never exposed to weatherapp or the browser.
  • Rate limiting on /api/ai/*, enforced server-side (per-user, per-day cap) to prevent cost abuse.
  • CORS on recommendation-service restricted to the known weatherapp origin only.
  • Onboarding input must be sanitized before being interpolated into any AI prompt, to prevent prompt injection.
  • Users must be able to delete their profile and all associated data (right-to-erasure), given the sensitivity of health-adjacent fields.

7.2 Assumptions Made in This TRD

  • "Monthly forecast" = 16-day extended forecast, not a climate-normal statistical outlook.
  • Health considerations are collected as a fixed, categorical list rather than free text — reduces liability and gives the rule engine/AI a controlled, predictable input set.
  • Onboarding is mandatory before first dashboard use, but individual fields (especially health) may be skippable — needs confirmation, see below.
  • Single AI provider active at a time (OpenAI or Groq), selected via environment variable.
  • English-only UI for this phase.

7.3 Open Questions

1. Should healthConsiderations be optional in onboarding, or mandatory? Recommend optional — mandatory disclosure raises both UX friction and data-sensitivity concerns.
2. Should users be able to skip onboarding entirely and get generic (non-personalized) recommendations? Recommend yes — reduces signup friction, still delivers core weather value.
3. Data retention: how long should logs and profile data persist after account deletion — immediate purge, or a grace period?
4. Auth provider: still Clerk from v1, or a custom JWT solution given the new service split?

08Error Handling Strategy

Failure PointHandling
Open-Meteo timeout/errorShow cached last-known data with a "stale data" badge; if no cache, inline error scoped to that widget only
Geocoding/search failure"Couldn't find that location" inline in search bar; other widgets unaffected
recommendation-service unreachableFrontend falls back to a generic, non-personalized weather-only view
AI provider timeout/errorAutomatic fallback to the deterministic rule engine (R-WA16) — user still gets a recommendation
AI returns malformed outputValidate response shape server-side before forwarding; on failure, use rule-engine fallback
Rate limit exceededClear 429 response; frontend shows "you've reached today's recommendation limit"
Invalid onboarding inputValidated both client-side and server-side — never trust client validation alone
Auth token expiredRedirect to login with a preserved "return to" URL

12Next Steps

Before implementation starts, confirmation is needed on:

  1. The three open questions in §7.3 (mandatory vs. optional health field, skip-onboarding option, data retention).
  2. The color palette additions in §10.
  3. Auth provider choice, since it determines auth.middleware.ts's implementation.

Once settled, the natural build order is: onboarding data model → recommendation-service API skeleton → rule engine (ship first, it's the safety net) → AI layer wrapping it → frontend integration last.
